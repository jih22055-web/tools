为什么 JWT 的 Payload 能直接读出来

2026-11-25 · 约 557 字

把一个 JWT 丢进解码器，中间那段立刻显示出 {"userId":123,"role":"admin"}。很多人第一反应是"这不就等于密码明文传输吗"——其实 JWT 从设计上就没打算保密。

JWT 的三段结构

一个 JWT 长这样：xxxxx.yyyyy.zzzzz，三段用点号分开：

  • Header（头部）：说明算法和类型，比如 {"alg":"HS256","typ":"JWT"}
  • Payload（载荷）：真正要传的数据，比如用户 ID、角色、过期时间
  • Signature（签名）：用密钥对前两段算出来的校验值

前两段用的都是 Base64URL 编码——就是 Base64 把 + 换成 -、/ 换成 _、去掉末尾 = 的变体，方便放进 URL。编码不等于加密，任何人拿到 token 都能解码出原文。JWT 解码器能直接读出 Payload，正是这个原因。

那签名是干嘛的

签名解决的是完整性和真实性，不是保密性。服务器签发 token 时，用只有自己知道的密钥对 Header.Payload 算一个签名附在后面。验证时服务器重算一遍签名，对得上就说明：

  • 这个 token 确实是本服务器签发的（不是伪造的）
  • 内容没有被中途篡改（改一个字符，签名就对不上）

所以 Payload 是"公开可读但改不了"。就像一张盖章的公开信，谁都能读内容，但没人能改内容还保留真印章。

因此有一条铁律

绝不能往 Payload 里放敏感信息：密码、身份证号、银行卡、密钥都不行。用户能解码看到，中间任何一层（代理、日志、浏览器历史）也都能看到。Payload 里只放非敏感的标识信息，比如用户 ID、角色、过期时间。

常见误区

  1. "用 JWT 就不用 HTTPS 了"：错。JWT 不加密，token 在传输中明文可见。被截获后，攻击者虽然改不了，但可以直接拿去冒充你（这叫重放）。HTTPS 必须开。
  2. 把 token 存在 localStorage 又不管 XSS：一旦页面有 XSS 漏洞，脚本能读走 token。这是 JWT 实践里最常见的失窃途径。
  3. 不设过期时间：Payload 里应该有 exp 字段，让 token 自动过期，缩短失窃后的风险窗口。

一句话：JWT 的 Payload 是 Base64URL 编码，不是加密，本来就能被任何人读出。它的安全靠签名保证"改不了"，不靠编码保证"看不到"。所以别放敏感信息，HTTPS 照开。
