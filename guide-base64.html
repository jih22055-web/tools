Base64 是什么，为什么它不是加密

2026-11-24 · 约 1200 字

很多人第一次见到 Base64 是在某个接口返回的一长串乱码里，5L2g5aW977yM5LiW55WM 这种东西，看起来像密文，于是顺手叫它「加密」。它不是。

它解决的是一个很土的问题

早期的网络协议（邮件、HTTP 头、URL）都是按文本设计的，只保证 ASCII 那 128 个字符能安全传输。可现实里要传的是图片、附件、二进制数据——这些字节里可能包含换行符、0x00 或者控制字符，一旦被协议当成命令解释，数据就毁了。

Base64 的办法很直接：把 3 个字节（24 位）切成 4 组 6 位，每组 6 位能表示 0–63，映射到 64 个「安全的」可打印字符上：A–Z、a–z、0–9、+、/，末尾补 =。

所以它的本质是换一套字母表来表示同样的数据，就像把十进制 255 写成十六进制 FF。任何人都能还原，因为没有密钥——没有密钥的东西不叫加密。

为什么体积会变大 33%

3 个字节变 4 个字符，4/3 ≈ 1.33。原本 1MB 的文件编码后大约 1.33MB。这就是为什么把图片转成 Base64 塞进 HTML 里，页面会明显变重——省了一次请求，但多背了三分之一的流量。

经验值：小于 2KB 的小图标（比如一个箭头）内联进 CSS 是划算的，能省一个 HTTP 请求；几十 KB 的照片内联进去就是自找麻烦，还会拖慢首屏渲染，因为 CSS 不解析完页面就出不来。

三个真实用途

1. data URI：把图片写进代码

background:url(data:image/png;base64,iVBORw0KGgo...)，浏览器看到 data: 就知道后面是内联数据，不用发请求。用图片转 Base64可以互相转换。

2. 邮件附件

SMTP 只能传 7 位 ASCII，附件全靠 Base64 编码塞进正文。一封带 10MB 附件的邮件，实际传输大约 13.3MB，就是这么来的。

3. JWT 令牌

JWT 的三段（Header.Payload.Signature）用的都是 Base64URL 变体——把 + 换成 -、/ 换成 _，并去掉末尾的 =，因为 + 和 / 在 URL 里有特殊含义。

这一点特别容易误解：JWT 的 Payload 是明文可读的，只是编码了。任何人拿到 token 都能解出里面的用户 ID、角色、过期时间。所以绝对不能把密码、手机号这类信息放进 Payload——要保密只能加密，而 JWT 的签名只保证「没被篡改」，不保证「看不见」。想验证一下可以拿现成的 token 去JWT 解码里解一遍。

中文乱码是怎么来的

Base64 编码的对象是字节，不是字符。「你好」这两个字先要变成字节，才有得编码。同一个「你好」：

  • 按 UTF-8 编码是 6 个字节 → 得到 5L2g5aW9
  • 按 GBK 编码是 4 个字节 → 得到完全不同的结果

如果编码时用 UTF-8、解码时按 GBK 去还原，就是典型的乱码。所以跨系统传 Base64，两边必须约定同一个字符集，现在默认都该用 UTF-8。用Base64 编码解码时如果出现乱码，先检查这一项，而不是怀疑工具坏了。

还有两个坑

换行符。按 MIME 规范，Base64 每 76 个字符要插一个换行。很多解码器不容忍正文里出现换行或空格，粘贴时最好先去掉。

末尾的等号。一个 = 表示原始数据差 2 个字节凑满 3 字节，两个 = 表示差 1 个。有些实现会把 = 去掉，解码时补回来即可，不影响内容。

一句话总结：Base64 是编码不是加密，谁都能解；体积涨三分之一；中文乱码九成是字符集不一致。
