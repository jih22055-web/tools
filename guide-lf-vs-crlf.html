换行符 LF 和 CRLF 有什么区别

2026-11-25 · 约 607 字

同一份代码从同事的 Windows 电脑拷到你手上，Git 显示整个文件都改了，每行末尾多了个 ^M；或者一个 shell 脚本在 Linux 上死活跑不起来，报错 bad interpreter。这两种现象的根子是同一个：换行符。

两个字符的来历

计算机出现之前是打字机。 carriage return（回车，\r，ASCII 13）把打印头移回行首，line feed（换行，\n，ASCII 10）把纸往上推一行。两件事要分两步做。

早期的操作系统在这个细节上分了家：

  • Unix / Linux / 现在的 macOS：只用一个 \n，因为它自己就代表"换到下一行行首"
  • DOS / Windows：沿用打字机的两步，用 \r\n 两个字节
  • 老版 Mac（Mac OS 9 之前）：只用 \r，现在几乎见不到

所以同样是"换行"，Windows 上的文本文件比 Linux 上每行多占一个字节。用十六进制看，LF 是 0A，CRLF 是 0D 0A。

为什么 Git 会显示整个文件都变了

Git 内部统一用 LF 存文本。但 Windows 上的工作区默认用 CRLF，于是 Git 在检出时把 LF 转成 CRLF，提交时再转回 LF。这套转换靠 core.autocrlf 控制：

  • Windows：git config core.autocrlf true（提交时转 LF，检出时转 CRLF）
  • Linux / macOS：git config core.autocrlf input（提交时转 LF，检出不动）

如果这台机器设了 true、那台设了 false，两边的行尾就不一致，Git 会把每一行的结尾差异都算成改动。稳妥的做法是提交一个 .gitattributes 文件，写一行 * text=auto，让 Git 自己判断哪些是文本并统一处理，不再依赖每个人的本地设置。

bad interpreter 是怎么来的

把 Windows 上写好的 shell 脚本传到 Linux，第一行 #!/bin/bash 末尾带着一个 \r。Linux 的内核找解释器时，找到的是名为 /bin/bash\r 的文件——当然不存在，于是报 /bin/bash^M: bad interpreter。^M 就是 \r 在终端里的可见写法。修复只要把行尾转回 LF：

  1. 用 sed -i 's/\r$//' script.sh 就地去掉行尾的 CR
  2. 或者安装 dos2unix，执行 dos2unix script.sh

反过来，如果 Linux 上的脚本被转成 CRLF，也可能出现命令末尾多一个看不见的字符、参数对不上的怪问题。

什么时候必须注意

  • Docker 镜像、CI 脚本、Makefile：这些几乎都在 Linux 容器里跑，CRLF 会直接导致构建失败
  • Python / Node 源码：大多数解释器能容忍 CRLF，但混用两种行尾会让 diff 变得没法看
  • CSV 文件：跨系统交换时行尾不统一，某些解析库会读出带 CR 的字段值

一句话：代码和脚本统一用 LF，只有在确实要给 Windows 程序看的时候才转 CRLF。想看清一个文件到底用的哪种行尾，用 ASCII 码表速查对照 0A 和 0D 两个字节即可。
